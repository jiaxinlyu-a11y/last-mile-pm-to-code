Fiction Workbench

A local, single-user workspace for planning and writing long novels. It organises outlines, characters and chapters as Markdown and JSON files, and compiles a bounded writing brief that the user hands to Codex. The app itself never calls an AI API. Every statement below was checked against the source code.

1. User flows: walk through one action

Each flow starts from one action in the app and follows the code until the data is stored. Every step lists what happened, the technologies used, and the files: path, what the file is for, and the function used in this step (a function is a named piece of code that does one job).

Main flows in this project
  1. Create a novel project (4 steps)
  2. Save a chapter (4 steps)
  3. Hand a chapter to Codex (6 steps)
  4. Delete a chapter and restore it (3 steps)
  5. Delete a whole project (2 steps)

Characters, volumes, relationships, timeline and foreshadowing records follow the same pattern: form → Server Action → Zod validation → file store with fingerprint check and temporary-file write. Shared libraries (personalities, emotions, prose rules) work the same way under fiction-library/.

Flow A: Create a novel project

Scenario: On the Project Library page you fill in a title, a project ID and a language, then click Create.

1
Submit the form Interface

The form sends its fields to a backend function and shows any field errors next to the inputs.

Technologies used
  • React: Draws the form and shows the result message
  • Next.js Server Actions: The form calls the backend function createNovelProjectAction directly
Files
  • src/ui/project-library.tsxProject Library page: project list and the create form
  • src/app/page.tsxHome page that shows the library
2
Validate the input Application

Every field is checked against a set of rules before anything touches the disk. Bad input returns an error per field; the chosen genres and styles must exist in the shared library.

Technologies used
  • Zod: Rule sheet for the input: ID format, title length, locale format
  • try / catch: Turns storage errors into a readable message
Files
  • src/app/actions.tsBackend entry for project actionscreateNovelProjectAction
  • src/modules/novel/validation/create-novel-project-input.tsRules for the create form
  • src/core/validation/project-id.tsRule for safe project IDs (lowercase letters, digits, hyphens)projectIdSchema
3
Build the project manifest Rules & validation

Creates the project's identity card (project.json) with a schema version, timestamps and the list of folders a novel project needs.

Technologies used
  • Schema version field: Stored in project.json so future versions can upgrade old projects
Files
  • src/modules/novel/application/create-novel-project.tsAssembles a new novel projectcreateNovelProject
4
Write it all-or-nothing Data access → Storage

Everything is first written into a hidden temporary folder. Each path is checked to stay inside that folder. Only when all files are in place is the folder renamed to its real name; on any error the temporary folder is deleted.

Technologies used
  • Node.js file system (fs): mkdir, writeFile and rename
  • Staging folder + rename: A half-created project can never appear
  • Path guard: assertPathWithinRoot rejects any path that escapes the folder
Files
  • src/infrastructure/filesystem/projects-root.tsAll reading and writing of project folderscreateProject, assertPathWithinRoot
  • fiction-projects/<project-id>/project.jsonThe new project's manifest

Flow B: Save a chapter

Scenario: You edit the outline, text or summary of a chapter and click Save.

1
Send the text and its fingerprint Interface

The editor sends the text plus the fingerprint (revision) of the version you opened.

Technologies used
  • React: Holds the editor text and shows “unsaved changes”
  • Next.js Server Actions: Calls saveChapterDocumentAction
Files
  • src/modules/novel/ui/chapter-editor.tsxThe chapter editor screenpersist: runs when you click Save
2
Check the input Application

The request must name a valid project, volume and chapter, the text must be under 4 MiB, and the fingerprint must be 64 characters long.

Technologies used
  • Zod: saveChapterDocumentInputSchema
Files
  • src/modules/novel/validation/chapter.tsAll rules for chapterssaveChapterDocumentInputSchema
  • src/app/projects/[projectId]/volumes/[volumeId]/chapters/actions.tsBackend entry for chapter actions (not readable in this test: path too deeply nested)saveChapterDocumentAction
3
Refuse if the file changed elsewhere Data access

The store re-reads the chapter and compares fingerprints. If the file on disk changed after you opened it (for example, Codex wrote to it), saving is refused with “changed on disk, please refresh”.

Technologies used
  • SHA-256 fingerprint: revision() turns a file's text into a 64-character fingerprint
Files
  • src/infrastructure/filesystem/chapter-store.tsAll reading and writing of chapterssaveChapterDocument
4
Write safely, then update metadata Data access → Storage

The text goes to a temporary file, is flushed to disk, then renamed over the real file. Then meta.json gets a new updated time. New fingerprints go back to the editor.

Technologies used
  • Temporary file + fsync + rename: writeStaged: the real file is never half-written
Files
  • src/infrastructure/filesystem/chapter-store.tsAll reading and writing of chapterswriteStaged, writeJson
  • fiction-projects/<id>/novel/volumes/<volume>/chapters/<chapter>/content.mdChapter text
  • …/chapters/<chapter>/meta.jsonChapter number, title, status, timestamps

Flow C: Hand a chapter to Codex

Scenario: On a chapter page you open the Codex writing panel and click Copy.

1
Compile a bounded brief Application

The app collects only what this chapter needs: the chapter outline; project, world, style and volume notes; one character card per selected character (with their relationships and personality-based guidance); a short prose sample; and the ending of the previous chapter.

Technologies used
  • Next.js server rendering: The brief is assembled on the server when the chapter page loads
  • Character projection: Merges profile, personality and relationships into one card per character
Files
  • src/modules/novel/application/chapter-drafting-context.tsGathers the materials for one chapterresolveChapterDraftingContext
  • src/modules/novel/application/character-profile-projection.tsBuilds the per-character card
2
Trim the previous chapter Application

Only the ending of the previous chapter is passed on: the whole text if it is 1,200 characters or less, otherwise about the last 1,000 characters, cut at a paragraph or line break.

Technologies used
  • Plain TypeScript: endingExcerpt counts Unicode characters and looks for a break
Files
  • src/modules/novel/application/previous-chapter-handoff.tsPrevious-chapter endingendingExcerpt
3
Turn it into an instruction Application

The IDs and word targets are validated again, and the brief is serialised as JSON between <compiled_chapter_context> tags, with the name of the Codex skill to call and the one file it may write.

Technologies used
  • Zod: Validates IDs and the word range
  • JSON: The brief is machine-readable for the Codex skill
Files
  • src/modules/novel/application/chapter-drafting-task.tsBuilds the text you paste into CodexcreateChapterDraftingTaskFromContext
4
Copy to clipboard Interface

Clicking Copy puts the instruction on the clipboard and shows a confirmation.

Technologies used
  • Browser Clipboard API: navigator.clipboard.writeText
Files
  • src/ui/codex-task-panel.tsxThe Codex writing panelcopyTask
5
Codex writes the chapter External AI

In VS Code, Codex runs the project's own skill. It re-checks every ID and path, refuses links that escape the project, and writes only that chapter's content.md. It does not change outlines, metadata or status.

Technologies used
  • Codex skill (SKILL.md): Written rules Codex must follow
Files
  • .agents/skills/novel-chapter-drafting/SKILL.mdThe drafting rules for Codex
  • …/chapters/<chapter>/content.mdThe only file Codex writes
6
Back in the app Interface → Data access

When you reopen the chapter, the editor shows the new text with a new fingerprint. If you had unsaved edits open from before, saving them is refused (see Flow B), so Codex's text is not overwritten by accident. Chapter status changes only when you change it.

Technologies used
  • SHA-256 fingerprint: Detects that the file changed
Files
  • src/infrastructure/filesystem/chapter-store.tsAll reading and writing of chaptersloadChapter, saveChapterDocument

The chapter page file that wires steps 1–4 together (src/app/projects/[projectId]/volumes/[volumeId]/chapters/[chapterId]/page.tsx) could not be read in this test because the path is too deeply nested for the file bridge.

Flow D: Delete a chapter and restore it

Scenario: You delete a chapter, then open the project's recycle bin and restore it.

1
Confirm by typing the ID Interface → Application

Deleting requires typing the full chapter ID. A mismatch stops the deletion.

Technologies used
  • Confirmation dialog: The user must type the exact ID
Files
  • src/infrastructure/filesystem/chapter-store.tsAll reading and writing of chaptersrecoverablyDeleteChapter: stops if the typed ID does not match
2
Move, don't delete Data access → Storage

The chapter folder is moved into .fiction-workbench/recovery/chapters/<volume>/<chapter>-<time>. Every folder on the way is checked to be a real folder inside the project, not a link pointing elsewhere.

Technologies used
  • rename: Moves the whole folder in one step
  • lstat + realpath: Reject symbolic links and paths outside the project
Files
  • src/infrastructure/filesystem/chapter-store.tsAll reading and writing of chaptersrecoverablyDeleteChapter, safeDirectory
  • fiction-projects/<id>/.fiction-workbench/recovery/Recycle bin storage
3
Restore Application → Data access

Restoring checks that nothing with the same ID now sits in the original place (it never overwrites), moves the folder back, and updates the book structure. If updating the structure fails, the move is undone and the item stays in the recycle bin.

Technologies used
  • Next.js Server Actions: restoreProjectRecoveryAction
  • Zod: Re-validates the stored JSON before using it
  • Undo on failure: Moves the folder back if the second step fails
Files
  • src/app/projects/[projectId]/recycle-bin/actions.tsBackend entry for recycle bin actionsrestoreProjectRecoveryAction
  • src/infrastructure/filesystem/recycle-bin-store.tsRecycle bin logicrestore
  • fiction-projects/<id>/novel/planning/book-structure.jsonOrder of volumes and chapters

Scenario: On the Project Library page you delete a project.

1
Confirm by typing the ID Interface → Application

  • Next.js Server Actions: deleteProjectAction

  • src/app/actions.tsBackend entry for project actionsdeleteProjectAction

The project path must sit directly inside the projects folder; then the whole folder is removed. There is no recycle bin for whole projects.

  • Path check: Refuses anything that is not a direct child of the projects folder

7. Interview self-test

Answer first, then open the key points. Ask an AI about anything you still don't get.

Frontend vs backendWhen you click Save in the chapter editor, how does the screen reach the backend? How can you tell which files run in the browser?

The editor calls a Next.js Server Action. Files that start with "use client" run in the browser; actions.ts files start with "use server" and run only on the server.

Why data is stored this wayWhy does this project use Markdown and JSON files instead of a database?

So that the user and Codex can open and edit the same files in VS Code, every change is readable, and each chapter is a folder that can be moved to the recycle bin and back. JSON holds the structured parts and is checked with Zod.

What if something failsCodex rewrites a chapter while you still have the old version open in the editor. What happens when you click Save?

The save is refused: the fingerprint of the file on disk no longer matches the one you opened, so you are asked to refresh.

What if something failsRestoring a chapter fails half-way. Is anything lost?

No. If the book structure cannot be updated, the folder is moved back into the recycle bin and an error is shown.

How the AI is constrainedHow is Codex kept from writing outside one chapter?

The app gives it a bounded brief with exact IDs and one output path; the Codex skill re-validates IDs and paths, rejects links, and may only write that chapter's content.md.

8. Surprises found in the code

  • The README says deleted projects go to fiction-projects/.trash/; the code deletes them permanently. The README is out of date.
  • One test file (src/ui/character-expression-workspace.test.tsx) exists but is not listed in vitest.config.mts, so it never runs.
  • Two files under src/app/projects/[projectId]/volumes/[volumeId]/chapters/ could not be read in this test because the path is too deeply nested for the file bridge; their role was inferred from the files that import them.
